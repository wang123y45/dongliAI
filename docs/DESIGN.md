# 设计理念

## 一句话

**不是把网页塞进一个窗口，而是把“冻梨AI”从一个网址，变成一个可以每天打开、长期驻留的桌面入口。**

网页版解决“随时随地可用”；桌面版解决“固定工位上的稳定、快速、可被系统识别”。两者共享同一套账号、数据与业务能力，不复制第二套聊天逻辑。

## 多端整体架构

```text
                        ┌──────────────────────────┐
                        │   web/  Node 工作台服务端  │
                        │  登录 / 会员 / 会话 / 语音  │
                        │  图片 / 技能 / 后台配置     │
                        └────────────┬─────────────┘
                                     │ HTTPS
        ┌────────────────────────────┼────────────────────────────┐
        │                            │                            │
   Web 浏览器                  Electron 桌面壳              Android / iOS 原生壳
   PWA / 响应式                Windows / macOS / Linux       WebView / WKWebView
```

- **服务端是唯一业务内核**：模型接口、账号、额度、会话、附件解析、TTS 都只在 `web/` 维护。
- **客户端只做平台能力**：窗口、生命周期、麦克风/相机权限、分享、外链、安全边界、分发。
- **为什么 iOS 不重写一套聊天**：重写会带来账号、会员、历史记录、技能插件四套同步问题；原生壳可以让 iOS 与网页在功能上保持同一版本。
- **为什么桌面用 Electron**：当前阶段用一套 JS 壳换取 Windows/macOS/Linux 一致交付，体积成本由 GitHub Actions 自动构建来抵消。
- **代价与边界**：客户端强依赖网络；离线只提供可重试页，不承诺离线对话。

## 三个原则

### 1. 单一事实来源

所有对话、会员、技能、上传、语音合成仍由现有服务端提供。桌面端只做壳层能力：

- 原生窗口与菜单
- 登录会话持久化
- 系统麦克风 / 通知权限
- 外链交给系统浏览器
- 断网兜底与版本分发

这样做的好处是：网页修一个 bug，桌面端立即受益；不会出现“网页一套、客户端一套”的双维护。代价是强依赖网络，所以必须把离线状态设计成可理解、可恢复的页面，而不是白屏。

### 2. 原生优先，品牌克制

窗口使用系统原生边框、原生菜单和系统字体。没有自定义标题栏，没有仿移动端的底部导航，也不把网页的侧栏再包一层“应用外壳”。

品牌只出现在三个地方：

- 应用图标
- 窗口标题
- 服务不可达时的离线页

其余界面交给工作台本身。桌面端的目标是“让工作台更顺手”，不是“再设计一个工作台”。

### 3. 安全边界先于便利

网页内容是远程内容，桌面端必须假设它可能被篡改或跳转：

- `nodeIntegration: false`
- `contextIsolation: true`
- `sandbox: true`
- preload 只暴露三个能力：重试、打开外链、读取版本号
- 只有冻梨AI 可信域名可以申请麦克风 / 通知权限
- 站外导航一律阻止并交给系统浏览器
- 禁止 `webview`，禁止运行不安全内容

这不是“多一层壳”，而是把浏览器里默认存在的权限收窄到业务真正需要的范围。

## 架构

```text
┌────────────────────────────────────────────┐
│ Electron Main Process                      │
│  ├─ 单实例锁 / 窗口状态                     │
│  ├─ 菜单 / 外链 / 权限策略                  │
│  ├─ 断网检测 → error.html                  │
│  └─ preload 最小 IPC 桥                    │
├────────────────────────────────────────────┤
│ BrowserWindow（sandboxed renderer）         │
│  └─ https://www.jhcmzy.top/dongli/         │
│      └─ 现有登录 / 对话 / 技能 / 语音       │
└────────────────────────────────────────────┘
```

- **主进程**拥有系统能力，渲染进程只拿到一个受限的 `window.desktop`。
- **远程页面**是唯一业务界面。`DONGLI_URL` 允许开发时指向本地 `19091`。
- **离线页**是本地 HTML，不依赖网络，负责解释失败原因并提供重试 / 打开网页版。

## 为什么是 Electron

| 方案 | 优点 | 代价 | 结论 |
|---|---|---|---|
| Electron | 一套 JS 代码，三平台行为一致；网页迁移成本最低；CI 成熟 | 安装包约 80–120 MB；内存高于原生 | 当前阶段采用 |
| Tauri | 包体小、内存低 | 需要 Rust 工具链；macOS / Linux 交叉构建和签名更复杂 | 后续可评估 |
| 原生三套 | 体验最好 | 三套代码、三套发布流程 | 不适合当前节奏 |

现阶段最重要的是“先让三平台用户装上、用上、能持续发版”。Electron 的体积成本，用 GitHub Actions 的自动化来换时间，是合理的。

## 交互细节

- **窗口记忆**：关闭时保存位置和尺寸；显示器拔掉后自动回退到默认尺寸，避免窗口出现在屏幕外。
- **单实例**：重复双击只聚焦已有窗口，不产生第二个登录态。
- **后台不降频**：`backgroundThrottling: false`，最小化后语音朗读不被系统节流。
- **权限最小化**：麦克风用于长按语音；通知用于回复完成提醒；其余权限默认拒绝。
- **外链策略**：GitHub、帮助文档、网页版都在系统浏览器打开，不在应用内叠加第二个浏览器。
- **错误可恢复**：失败页给出“重新连接”和“打开网页版”，技术详情折叠，不把堆栈甩给用户。

## 跨平台差异

- **Windows**：NSIS 安装包，创建桌面和开始菜单快捷方式；未签名时会有 SmartScreen 提示。
- **macOS**：Universal DMG / ZIP，同时覆盖 Apple Silicon 与 Intel；未公证时需在隐私与安全性中放行。
- **Linux / Ubuntu**：AppImage 便于直接运行，DEB 便于系统集成；不同发行版的库依赖可能不同。

桌面端不试图把三平台做成完全一样的皮肤，而是让每个平台保留自己的窗口、菜单和安装习惯。

## 分发理念

**代码公开，构建公开，产物公开。**

- 源码在 GitHub 公开，任何人可以审阅、复刻、提交 issue。
- 构建在 GitHub Actions 上完成，构建脚本和产物来源可追溯。
- 版本通过 Git tag 触发，安装包挂到 GitHub Release；网页端只负责引导下载。
- 不把安装包散落在网盘或聊天记录里，避免“这个版本是谁打的”无法回答。

## 后续路线

1. **自动更新**：接入 `electron-updater`，读取 GitHub Releases 的 `latest.yml`。
2. **系统托盘 / 全局快捷键**：让“呼出工作台”变成一个动作，而不是找窗口。
3. **代码签名**：Windows EV 证书、Apple Developer ID + notarization。
4. **包体优化**：评估 Tauri 或按平台裁剪 Electron。
5. **可观测性**：崩溃上报、启动耗时、更新成功率；默认关闭内容级数据采集。

## 不做什么

- 不复制一套聊天后端。
- 不接管用户在网页里的账号密码。
- 不读取浏览器 Cookie、系统钥匙串或本地会话文件。
- 不在应用内静默执行远程脚本或下载可执行文件。
- 不为了“像原生”而重画一套与网页不一致的导航。
